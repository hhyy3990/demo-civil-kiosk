# 무인민원발급기 — 공통 접근성 SDK v0.5.6 설치 및 실제 레이아웃 보정

현재 프로젝트는 **무인민원발급기 시뮬레이션 키오스크**입니다.

이 프로젝트에는 기존 공통 SDK `@naebangsik/kiosk-accessibility-sdk@0.5.5`가 설치되어 있습니다.

데모커피 프로젝트에서 개발한 새 SDK tarball `naebangsik-kiosk-accessibility-sdk-0.5.6.tgz`를 업로드했습니다.

이번 작업의 목적은 다음과 같습니다.

1. 기존 SDK v0.5.5를 v0.5.6으로 안전하게 교체
2. QR v3 하단 조작 모드의 자동 동기화 기능 통합
3. 큰 글씨에서 무인민원발급기 하단 안내 문구가 잘리거나 겹치는 현상 진단
4. SDK의 선택적 5~10% 글씨 크기 보정 적용
5. 보정 후 다른 콘텐츠와 새로운 겹침이 발생하지 않는지 검증
6. 기존 민원발급 업무 흐름과 SDK 기능의 회귀 테스트

**이번 작업에서 중앙 QR 서버, 데모커피 프로젝트, SDK 패키지 소스는 수정하지 마세요.**

---

## 1. SDK v0.5.6 설치

업로드된 `naebangsik-kiosk-accessibility-sdk-0.5.6.tgz`의 실제 파일 위치를 확인하세요.

패키지 내부 메타데이터를 먼저 검사합니다.

- name: `@naebangsik/kiosk-accessibility-sdk`
- version: `0.5.6`

메타데이터가 일치하는 경우에만 기존 v0.5.5를 교체합니다.

설치한 뒤 다음을 확인하세요.

- package.json 의존성
- lockfile 일치
- 실제 설치된 SDK 버전
- 공개 타입 선언
- 기존 import 및 API 호환성

패키지가 없거나 설치가 실패하면 임의로 v0.5.6을 재구현하지 말고 중단 후 보고하세요.

기존 v0.5.5로 복원할 수 있는 상태를 유지하세요.

## 2. 기존 무인민원발급기 구조 먼저 분석

수정 전에 다음 파일과 연결 구조를 확인합니다.

- `src/useKioskAccessibility.ts`
- `src/styles.css`
- 실제 하단 안내 문구를 렌더링하는 컴포넌트
- 처음화면·전화면 버튼
- QR 진입 도크 및 모달
- 키오스크 메인 콘텐츠 및 스크롤 컨테이너

현재 구현에서 다음 영역의 역할을 구분하세요.

- 화면 고정 조작부
- 스크롤 가능한 업무 콘텐츠
- 일반 안내 문구
- SDK QR 도크
- 모달 영역

기존 CSS에 임시 여백이나 도크 공간을 이중 예약하는 코드가 없는지도 확인합니다.

기존에 해결한 `justify-content: safe center` 동작과 165px 중복 공간 제거 수정은 유지해야 합니다.

## 3. QR 도크 자동 동기화 통합

기존 무인민원발급기에는 QR v3의 `preferences.viewportMode`를 읽고, 호스트에서 QR 도크 `bottomViewportPercent`를 별도로 갱신하는 보조 코드가 있을 수 있습니다.

SDK v0.5.6은 이 동기화를 내부에서 처리하므로, 기존 호스트 코드와 충돌하거나 중복되지 않도록 점검합니다.

단, **호스트 코드를 무조건 삭제하지 마세요.**

우선 다음을 확인합니다.

1. SDK가 실제로 `applyProfile()` 이후 활성 도크의 위치를 변경하는지
2. 호스트에서 명시한 `bottomViewportPercent`가 개발용 우선 설정으로 남아 있는지
3. 기존 호스트 코드 제거 후에도 QR 모달, 카메라, 수동 토큰 입력이 정상인지
4. React 렌더링과 도크 갱신의 순서 문제는 없는지
5. 이전에 발생했던 불필요한 165px 빈 공간이 재발하지 않는지

SDK 자체 동기화가 정상임을 확인한 경우에만 불필요해진 호스트 코드를 제거하거나 단순화합니다.

특히 기존 `bottomViewportPercent` 명시값이 SDK의 프로필 기반 동기화를 덮어쓰지 않는지 확인하세요. 필요한 경우 명시적인 개발용 override를 제거하되 다른 도크 설정은 보존합니다.

검증할 상태:

- QR v3 viewportMode null
- QR v3 하단 60%
- QR v3 하단 70%
- QR v3 하단 80%
- 구형 QR v1/v2
- `endSession()` 이후 일반 모드 복귀

QR 도크가 중복 생성되면 실패입니다.

## 4. 하단 글자 잘림 문제 진단

현재 확인된 문제는 큰 글씨 또는 매우 큰 글씨 모드에서 무인민원발급기 아래쪽 안내 문구가 겹치거나 잘리는 현상입니다.

특히 다음과 같은 보조 문구가 위치한 하단 영역을 조사합니다.

- 민원 발급 시뮬레이션 안내
- 실제 신청 정보가 저장되지 않는다는 안내

실제 문구와 DOM 구조는 코드를 통해 확인하세요.

다음 좌표를 실제 브라우저에서 측정합니다.

- 안내문 bounding rectangle
- 안내문 부모 컨테이너
- 하단 고정 버튼 영역
- QR 도크
- 메인 스크롤 영역
- 실제 보이는 작업 영역
- 요소의 scrollHeight/clientHeight
- 요소의 scrollWidth/clientWidth
- computed font-size 및 line-height
- overflow 속성
- 실제 hit-testing 결과

**문구의 문제 원인이 텍스트 크기인지, 부모 높이 부족인지, 다른 고정 요소의 덮임인지 먼저 구분하세요.**

화면을 보기 좋게 보이게 하려고 위치나 크기를 임의로 변경하지 마세요.

## 5. 선택적 글씨 크기 보정 적용

새 SDK에 추가된 `getFontCorrectionTargets()`를 사용합니다.

무인민원발급기의 **축소해도 되는 보조 안내 문구만** 명시적으로 등록합니다.

SDK의 실제 공개 타입과 README를 확인한 후 정확한 API 형식으로 연결하세요. 함수 시그니처를 추측하지 마세요.

보정 원칙:

- 큰 글씨 모드 유지
- 매우 큰 글씨 모드 유지
- 먼저 5% 보정
- 필요한 경우 최대 10% 보정
- 실제 겹침·잘림이 완전히 해결된 경우에만 보정 유지
- 해결되지 않으면 SDK 확대 상태로 복원
- 기존 호스트 원본 스타일 및 line-height 복원
- 사용자 설정을 해제하면 기존 크기로 복원

절대 보정 대상으로 등록하지 말아야 할 것:

- 주민등록번호 입력 화면의 필수 안내
- 개인정보 및 경고 문구
- 증명서 종류 및 메뉴명
- 결제 금액과 수수료
- 주요 버튼 텍스트
- 오류 메시지
- 사용자 입력 데이터

실제 '정보가 저장되지 않는다'는 안내가 개인정보 관련 필수 고지에 해당한다면 **자동 축소 대상으로 등록하지 말고**, 별도 레이아웃 수정이 필요한 항목으로 보고하세요.

**모든 안내 문구를 한꺼번에 등록하지 마세요.**

## 6. 줄바꿈 및 강제 이동 금지

문제가 발생했다고 다음 방법으로 임시 해결하지 마세요.

- 모든 문구를 강제로 여러 줄로 표시
- 안내문을 임의의 스크롤 영역으로 이동
- 음수 margin 사용
- position:absolute로 덮어쓰기
- QR 도크를 가리기
- 필수 안내문을 숨기기
- overflow:hidden으로 잘린 부분 감추기
- 화면 전체를 scale()로 축소
- 하단 버튼을 문구 위에 겹치게 배치
- 큰 글씨 모드를 해제
- 글씨를 10% 초과 축소

줄바꿈이 높이를 증가시켜 고정 조작부와 충돌하는 상황은 허용하지 않습니다.

SDK 보정으로 해결되지 않는 경우에는 실패 진단을 보존하고, 필요한 최소 레이아웃 수정안을 제안하세요.

필수 안내가 잘려 있다면 단순히 진단 결과만 남기고 성공 처리해서는 안 됩니다.

## 7. 개발자용 레이아웃 진단 연결

SDK의 `inspectLayout()`을 사용합니다.

실제 타입 선언과 README를 참조하세요.

개발 환경에서 다음 상황을 검사합니다.

- 일반 글씨
- 큰 글씨
- 매우 큰 글씨
- 큰 버튼
- 하단 60%
- 하단 70%
- 하단 80%
- 큰 글씨 + 큰 버튼 + 하단 60%
- 매우 큰 글씨 + 큰 버튼 + 하단 70%
- 매우 큰 글씨 + 큰 버튼 + 하단 80%

진단 결과에는 가능하면 다음을 포함합니다.

- 화면 크기
- 적용 프로필
- 현재 업무 단계
- 안내문 원래 글씨 크기
- 보정 후 글씨 크기
- 실제 보정률
- 텍스트 잘림 여부
- 고정 버튼 충돌 여부
- QR 도크 충돌 여부
- 마지막 버튼 접근 여부
- 스크롤 가능 여부
- SDK 진단 결과

개발자 전용으로만 사용하고 실제 사용자 화면에는 진단 패널을 표시하지 않습니다.

주민등록번호, 인증 정보, 결제 정보 등 사용자 입력값을 출력하거나 로그에 남기지 마세요.

## 8. 보정 결과에 따른 판단

다음 기준으로 처리합니다.

### A. 5% 보정으로 완전히 해결되는 경우

5% 보정을 유지하고 실제 겹침이 사라졌는지 확인합니다.

### B. 10% 이내 보정으로 완전히 해결되는 경우

필요한 최소 보정률을 적용하고 확인합니다.

### C. 10% 보정으로도 해결되지 않는 경우

추가 축소하지 않고 원래 접근성 확대 상태를 유지합니다.

다음 정보를 보고합니다.

- 무엇과 무엇이 겹치는지
- 실제 겹침 크기
- 원인이 되는 CSS/DOM 구조
- 최소한으로 필요한 레이아웃 변경
- SDK 공통 수정이 필요한 문제인지, 이 호스트의 배치 문제인지

이 경우 무리하게 자동 수정하지 말고, **안내문이 가려지지 않도록 하는 최소 호스트 레이아웃 수정안**을 제시하세요.

단순 장식 문구와 필수 안내 문구를 구분하세요.

## 9. 화면별 브라우저 검증

다음 화면 크기를 검증합니다.

- 320×844
- 360×667
- 390×844
- 1080×1920
- 1440×900
- 1920×1080

특히 360×667에서 하단 60·70·80% 모드를 집중 검증합니다.

각 경우에 다음을 확인합니다.

- 첫 제목이 가려지지 않는지
- 하단 안내문을 실제로 읽을 수 있는지
- 처음화면 버튼을 누를 수 있는지
- 전화면 버튼을 누를 수 있는지
- 마지막 증명서 메뉴까지 도달할 수 있는지
- QR 도크와 버튼이 겹치지 않는지
- 스크롤 최하단이 안정적인지
- 개발자 진단과 실제 화면 상태가 일치하는지

단순 스크린샷뿐 아니라 DOM 좌표, scrollHeight/clientHeight, 실제 클릭 가능 위치도 확인하세요.

최종 성공 기준은 단순히 SDK를 v0.5.6으로 올리는 것이 아니라, 기존 기능을 보존하면서 하단 안내문이 실제로 읽히고 필수 버튼이 가려지지 않는지 확인하는 것입니다.

만약 자동 5~10% 보정만으로 해결되지 않는다면, 실패 원인을 정확히 보고하고 안전한 수정안을 제안하세요. 잘리거나 겹치는 상태를 정상으로 처리하지 마세요.
