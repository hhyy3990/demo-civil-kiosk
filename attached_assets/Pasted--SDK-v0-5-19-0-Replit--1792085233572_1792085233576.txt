# 무인민원발급기 — 공통 SDK v0.5.19 설치 및 안내 누락·레이아웃 안정화

## 0. 작업 대상 및 기본 원칙

현재 프로젝트는 **무인민원발급기 Replit**입니다.

첨부된 `naebangsik-kiosk-accessibility-sdk-0.5.19.tgz`를 사용하여 기존 SDK v0.5.15를 **v0.5.19로 업데이트**해 주세요.

패키지명: `@naebangsik/kiosk-accessibility-sdk`

이번 작업의 목표는 다음 세 가지입니다.

1. 최신 공통 SDK v0.5.19 설치
2. 기존에 발견된 쉬운 말·스마트 길잡이 안내 누락 원인 조사 및 해결
3. 일반 화면과 하단 조작 모드에서 안내창·키패드·주요 버튼의 안정적인 배치 검증

**가장 중요한 개발 원칙은 SDK-first입니다.**

공통으로 해결해야 하는 문제는 반드시 데모커피 프로젝트에서 관리하는 공통 SDK 원본을 수정해야 합니다.

무인민원발급기에서는 SDK 공개 API를 연결하거나 실제 업무 단계에 안내 문구를 전달하는 작업만 수행합니다.

호스트별 안내창 CSS, 독자적인 안내창, 임시 위치 고정, 반복 scrollTo 우회는 금지합니다.

SDK 자체의 결함이 발견되면 이 프로젝트에서 임의로 수정하지 말고 재현 조건을 보고하세요.

## 3. 이전에 발견된 안내 누락 문제 조사

사용자가 실제 무인민원발급기에서 다음 문제를 발견했습니다.

### 쉬운 말 안내가 나타나지 않았던 화면

1. 오른손 엄지손가락을 올려 지문을 확인하는 화면
2. 증명서에 표시할 항목을 선택하는 화면
3. 수수료 면제 대상을 선택하는 화면
4. 발급할 부수를 입력하는 화면

### 스마트 길잡이가 나타나지 않았던 화면

5. 신청 내용을 최종 확인하는 화면

**이번에는 위 다섯 화면을 반드시 개별 검증하세요.**

각 화면에 대해 다음을 기록하세요.

- 실제 업무 화면 이름과 내부 screen ID
- SDK에 전달되는 `stepId`
- `setEasyLanguageState()` 호출 여부
- 실제 explanations 개수 및 내용 유무
- `setGuideState()` 호출 여부
- 스마트 길잡이 활성화·대기 상태
- 안내 DOM 생성 여부
- 화면 내 실제 표시 여부
- `guide-suppressed` 발생 여부
- 누락이 SDK 내부 문제인지 호스트 데이터 전달 문제인지

민감정보나 실제 주민등록번호를 로그에 남기지 마세요.

## 4. 안내 누락 수정 원칙

원인을 먼저 특정한 뒤 수정하세요.

### A. 호스트가 안내 데이터를 전달하지 않은 경우

해당 업무 화면에 적합한 쉬운 말 설명이나 스마트 길잡이 문구를 추가하고, 기존 SDK 공개 API에 연결하세요.

이것은 허용되는 호스트 어댑터 수정입니다.

### B. SDK가 데이터를 받았지만 표시하지 못한 경우

무인민원발급기에서 우회하지 마세요.

- 재현 화면
- 호출 순서
- stepId
- 안내 데이터 유무
- 브라우저 표시 상태
- 배치·숨김 진단

을 정리해 보고하세요.

공통 SDK 원본을 수정할 수 있도록 문제를 분리합니다.

### C. 내용이 없는 상태

빈 설명에 대해 안내창이나 펼치기 버튼을 표시하면 안 됩니다.

이전 단계의 설명을 그대로 재사용해서도 안 됩니다.

## 5. 업무 단계별 안내 내용 점검

현재 무인민원발급기의 실제 업무 화면을 기준으로 안내 내용을 검토하세요.

아래 문구는 예시이며 실제 화면에 존재하는 기능과 일치하도록 작성해야 합니다.

### 지문 확인

- 지문 확인: 화면에서 안내하는 손가락을 표시된 위치에 올려주세요.
- 지문 인식: 손가락의 지문으로 본인 여부를 확인하는 과정입니다.

실제 지문 인식이 아닌 시뮬레이션임을 오해하지 않게 유지하세요.

### 증명서 표시 항목 선택

- 표시 항목: 증명서에 어떤 정보를 넣을지 고르는 것입니다.
- 공개: 선택한 정보가 증명서에 표시된다는 뜻입니다.
- 미포함: 해당 정보를 증명서에 표시하지 않는다는 뜻입니다.

### 수수료 면제 대상

- 수수료: 서류를 발급받을 때 내는 비용입니다.
- 수수료 면제: 정해진 조건에 해당하면 발급 비용을 내지 않는 것입니다.
- 면제 대상: 수수료를 내지 않아도 되는 조건에 해당하는 사람을 뜻합니다.

실제 시뮬레이션의 선택지와 설명이 일치해야 합니다.

### 발급 부수

- 발급 부수: 서류를 몇 장 받을지 고르는 것입니다.
- 1부: 서류 한 장을 뜻합니다.

### 신청 내용 확인

스마트 길잡이 예시:

"신청한 증명서와 발급 부수, 선택한 내용을 확인해 주세요. 맞다면 화면의 확인 버튼을 눌러 다음 단계로 진행하세요."

실제 화면에 해당 버튼이 있는지 확인한 후 문구를 확정하세요.

**이 다섯 화면뿐 아니라 전체 업무 흐름에서 안내가 필요한 화면이 누락되어 있는지도 조사하세요.**

필요하다면 기존 4개 큰 단계와 실제 세부 화면의 관계를 정리하고, `stepId`를 세부 화면별로 안정적으로 구분하세요.

다만 새로운 민원발급 업무를 추가하지 마세요.

## 6. 쉬운 말 안내의 표시 시점

쉬운 말 안내는 해당 업무 화면에 진입한 직후 표시되어야 합니다.

스마트 길잡이가 시작된 다음에야 쉬운 말이 나타나는 동작은 허용하지 않습니다.

정상 흐름:

1. 업무 화면 진입
2. 해당 화면의 쉬운 말 설명 즉시 표시
3. 기존 대기시간 10/15/20초 경과
4. 스마트 길잡이 표시
5. 기본 10초 또는 천천히 15초 유지
6. 이전 쉬운 말 페이지·접힘 상태로 복귀

설명이 여러 개면 이전·다음으로 이동합니다.

스마트 길잡이에서는 페이지 번호와 이전·다음 버튼이 없어야 합니다.

## 7. 안내창 배치 및 디자인 검증

v0.5.19의 개선 사항을 그대로 활용하세요.

- 한 줄 헤더
- 간결한 접기·펼치기 버튼
- 44×44px 이상의 터치 영역
- 설명이 여러 개일 때만 이전·다음 표시
- 스마트 길잡이는 단일 안내
- 정보 아이콘 공간 축소
- 스크롤 시 안내 유지
- 주요 버튼·키패드 비가림
- 기존 위치 우선 배치
- 무한 재측정 방지

다음 환경을 확인하세요.

**일반 화면**
- `viewportMode: null`

**하단 조작**
- 60%
- 70%
- 80%

각 모드에서 글씨 매우 크게·버튼 크게·고대비·쉬운 말·스마트 길잡이를 함께 켠 상태도 테스트하세요.

화면 크기:

- 320×844
- 360×667
- 390×844
- 1080×1920

특히 다음을 확인하세요.

- 숫자 키패드 실제 클릭
- 입력한 값 표시
- 발급 항목 선택
- 부수 선택
- 결제 버튼
- 다음·이전 버튼
- 체험 종료
- QR 도크
- 스크롤 안내

주요 업무 버튼이 안내창 아래 가려져서는 안 됩니다.

스크롤해야 접근 가능한 요소는 실제로 스크롤해서 클릭할 수 있는지 확인하고, 스크롤 안내가 적절하게 제공되는지 확인하세요.

## 8. 안내창 스크롤·상태 복원 검증

다음 흐름을 실제 브라우저에서 확인하세요.

1. 쉬운 말 설명 표시
2. 다음 버튼으로 설명 2/3 이동
3. 화면 스크롤 10회
4. 설명이 사라지지 않는지 확인
5. 안내창 접기
6. 스마트 길잡이 시작
7. 접힌 상태 유지
8. 펼쳤을 때 스마트 길잡이 단일 문구 표시
9. 카운트다운 진행
10. 길잡이 종료
11. 쉬운 말 설명 2/3 복원
12. 접힘 상태 복원
13. 다음 업무 화면으로 이동
14. 이전 안내가 남지 않는지 확인

실제로 설명이 3개 미만인 화면이라면 해당 개수에 맞춰 검사하고, 독립 테스트에서는 3개 시나리오를 별도로 구성할 수 있습니다.

## 9. Development 접근성 체험 기능 유지

현재 구현된 '접근성 체험하기' 버튼은 그대로 유지합니다.

고정 프로필:

- textSize: extraLarge
- buttonSize: large
- contrast: high
- easyLanguage: true
- smartGuide: true
- guideDelaySeconds: 10
- slowGuidance: true
- viewportMode: bottom 60%
- language: ko
- voiceGuidance: false

현재 프로필의 다른 v4 필드도 유지합니다.

다만 일반 화면 테스트는 Development 내부에서 별도 모의 프로필로 진행할 수 있습니다.

Production에서는 체험 버튼과 테스트 프로필을 노출하면 안 됩니다.
