# 내 방식 QR — 무인민원발급기 SDK 예약 공간 165px 발생 원인 집중 진단

현재 무인민원발급기에는 공통 SDK `@naebangsik/kiosk-accessibility-sdk@0.5.5`가 설치되어 있습니다.

360×667 화면에서 하단 60% 모드를 적용하면 마지막 증명서 메뉴 뒤에 약 338.75px의 여백이 발생합니다.

이 중 165px은 이전 진단에서 SDK의 `.stage::after` 예약 공간으로 측정됐습니다.

그러나 데모커피 SDK 개발 프로젝트의 독립 소비자 테스트에서는 같은 높이의 QR 도크(72px)와 고정 조작부(93px)를 등록해도 SDK의 추가 스크롤 끝 예약 공간이 0px이었습니다.

따라서 이번에는 **왜 실제 무인민원발급기에서만 165px이 나타나는지**를 확인하려고 합니다.

이번 작업은 진단 전용입니다. 앱 코드, CSS, SDK 파일, 패키지 버전을 변경하지 마세요.

## 1. 실제 예약 공간의 출처 확인

360×667, 큰 글씨·큰 버튼·고대비, 하단 60%에서 다음을 조사합니다.

- 실제 스크롤 소유자 `<main class="stage">`
- `.stage::after`의 computed style
- `content`, `display`, `height`, `min-height`, `margin`, `padding`
- 해당 가상 요소의 스타일 선언 출처
- SDK가 만든 스타일인지 호스트가 만든 스타일인지
- 실제 scrollHeight에 기여하는 높이
- SDK가 설정한 safeInset 값
- 등록된 QR 도크 및 고정 조작부의 boundingClientRect

특히 **CSS에서 계산된 `::after` 높이가 165px이라는 사실과 실제 scrollHeight에 165px이 추가됐다는 사실을 구분해서 검증**해 주세요.

## 2. QR 도크 활성 상태별 비교

다음 상태를 순서대로 측정합니다.

A. 새로고침 직후 기본 첫 화면

B. QR 설정 모달을 연 상태

C. v3 하단 60% 프로필 적용 직후

D. 프로필 적용 1초 후

E. 증명서 선택으로 업무 화면 진입

F. 업무 화면에서 다른 단계로 전환

G. 처음화면 복귀 및 endSession() 이후

각 단계에서 다음을 기록합니다.

- QR 도크 실제 표시 여부
- QR 도크 active 상태
- QR 도크 실제 높이
- 고정 조작부 위치
- SDK viewport top/bottom/height
- `.stage::after` computed height
- `.stage`의 scrollHeight/clientHeight
- SDK 예약 공간과 마지막 메뉴 이후 여백

**QR 도크가 비활성화된 업무 화면에서도 도크 높이가 예약되는지**를 중점적으로 확인합니다.

## 3. 등록 영역과 실제 DOM 일치 여부

현재 `getLayoutRegions()`의 반환값과 실제 DOM을 비교합니다.

- scrollArea가 정확히 `<main class="stage">`인지
- contentRoot가 어떤 요소인지
- bottomControls에 무엇이 등록되는지
- QR 도크가 SDK에서 직접 관리되는지
- 같은 고정 조작부가 중복 등록되는지
- 숨겨진 요소도 높이 계산에 포함되는지
- 같은 요소가 두 영역에 중복으로 사용되는지

SDK API의 사용 방식이 올바른지 확인하고, 잘못 연결된 항목이 있다면 구체적으로 보고해 주세요.

## 4. 165px 발생 시점 확인

SDK 적용 전후를 비교해 주세요.

- QR 미적용
- v3 viewportMode:null
- 하단 60%
- 하단 70%
- 하단 80%

각 상태에서 `::after`의 높이와 실제 scrollHeight 증가량을 기록합니다.

필요하면 브라우저 안에서 일회성으로 가상 요소의 영향을 제거하는 진단을 수행할 수 있지만, 앱이나 SDK 파일에는 저장하지 않습니다.

이 실험으로 실제 스크롤 끝이 얼마나 줄어드는지 확인해 주세요.

실험 후 원래 상태로 복구합니다.

## 5. SDK 코드 경로 추적

설치된 v0.5.5 SDK의 다음 부분을 조사합니다.

- bottom viewport 높이 및 inset 계산
- fixed control 영역 등록
- QR 도크 활성화·비활성화
- safeInset 계산
- `::after` 예약 공간 생성 조건
- ResizeObserver와 레이아웃 재측정
- 화면 전환 시 예약 공간 갱신
- endSession() 시 스타일 복원

이전에 제작한 독립 fixture와 어떤 DOM 구조 또는 초기화 순서 차이가 있는지도 확인해 주세요.

추정만으로 원인을 확정하지 말고, 실제 실행 경로와 측정값을 연결해 설명해 주세요.

## 6. 원인 판정

결과를 다음 중 하나로 분류합니다.

**A. SDK 공통 결함:** 올바른 정보가 전달돼도 SDK가 이미 확보한 공간을 중복 예약합니다.

**B. 호스트 연결 문제:** SDK에 고정 요소나 스크롤 영역을 잘못 전달했거나 같은 공간을 중복 등록했습니다.

**C. 레이아웃 상호작용:** 호스트의 기존 콘텐츠 여백과 SDK의 예약 방식이 결합해 중복 공간이 발생합니다.

**D. 이전 측정 해석 오류:** 165px이 실제 SDK의 추가 예약 공간이 아니라 CSS 계산값 또는 이미 반영된 영역이었습니다.

원인을 판정할 수 없다면 어떤 정보가 부족한지 구체적으로 보고합니다.
