# 무인민원발급기 — SDK v0.5.6 자동 글씨 보정 실패 원인 정밀 진단

현재 무인민원발급기에는 `@naebangsik/kiosk-accessibility-sdk@0.5.6`이 설치되어 있습니다.

이번 작업의 목적은 **큰 글씨 모드에서 하단 안내 문구가 고정 조작부와 겹치는 현상이 왜 SDK의 5~10% 자동 보정으로 해결되지 않았는지 정확히 확인하는 것**입니다.

중요: 이번에는 진단만 진행합니다. 호스트 CSS, 업무 로직, SDK 패키지 소스를 수정하지 마세요. 브라우저 테스트에서 임시로 스타일을 변경해 측정하는 것은 허용하지만, 테스트 후 반드시 원래 상태로 복원해야 합니다.

## 1. 현재 문제 재현

이전 측정 결과는 다음과 같습니다.

- `.footer-service` 높이: 20px
- 360×667 기본 글씨 7px: 겹침 없음
- 360×667 큰 글씨 14px: 콘텐츠 30px, 조작부와 3px 겹침
- 360×667 매우 큰 글씨 16px: 콘텐츠 34px, 조작부와 7px 겹침
- 390×844 매우 큰 글씨 16px: 조작부와 7px 겹침

먼저 실제 브라우저에서 이 결과가 재현되는지 확인하세요.

## 2. 글씨 크기별 강제 축소 실험

다음 두 상태를 각각 검사합니다.

A. 큰 글씨 14px

B. 매우 큰 글씨 16px

각 상태에서 다음 네 경우를 비교하세요.

1. 원래 크기: 100%
2. 원래 크기의 95%: 5% 축소
3. 원래 크기의 90%: 10% 축소
4. 원래 크기로 복원한 후 상태

예상 비교 크기:

- 14px → 13.3px → 12.6px
- 16px → 15.2px → 14.4px

위 값은 계산 예시이므로 실제 적용 크기는 computed style로 확인하세요.

각 상태에서 다음을 측정합니다.

- 실제 computed font-size
- 실제 computed line-height
- 문구별 줄 수
- 문구별 bounding rectangle
- 푸터 부모 높이
- 푸터 scrollHeight/clientHeight
- 고정 조작부 시작 좌표
- QR 도크 시작 좌표
- 조작부와의 실제 겹침 px
- QR 도크와의 실제 겹침 px
- 텍스트 잘림 여부

특히 **폰트 크기를 줄여도 줄 수나 line-height가 그대로여서 전체 높이가 줄어들지 않는지** 확인하세요.

임시 스타일은 DOM 측정용으로만 적용하고, 테스트 종료 시 원래 스타일로 정확히 복원하세요.

## 3. 두 안내 문구를 구분해서 검사

현재 하단에는 다음 두 종류의 문구가 있습니다.

- '민원 발급 시뮬레이션' 안내
- '실제 신청 정보는 저장되지 않습니다' 안내

현재 SDK의 자동 보정 대상은 첫 번째 문구이고, 두 번째 개인정보 관련 안내는 축소 대상에서 제외된 것으로 보고됐습니다.

다음 세 경우를 구분해 측정하세요.

A. 첫 번째 보조 문구만 5~10% 축소

B. 두 문구 모두 크기를 유지

C. 원인 분석을 위한 격리 실험으로만 두 문구 모두 5~10% 축소

C는 실제 서비스 적용을 위한 변경이 아닙니다. 개인정보 관련 안내를 SDK 보정 대상으로 등록하거나 영구 축소하면 안 됩니다. 결과 측정 후 즉시 복원하세요.

이를 통해 보정 대상이 아닌 두 번째 안내 문구가 전체 푸터 높이를 결정하는지 확인합니다.

## 4. SDK 자동 보정 실패 조건 확인

SDK v0.5.6의 공개 API, 타입 선언 및 설치된 코드의 실제 동작을 분석하세요.

다음 사항을 확인합니다.

- `getFontCorrectionTargets()` 등록 결과
- 실제로 등록된 DOM 요소
- SDK가 처음 문제를 감지한 시점
- 5% 축소가 실제로 시도됐는지
- 10% 축소가 실제로 시도됐는지
- 시도 후 어떤 좌표와 높이를 측정했는지
- 어떤 조건 때문에 실패로 판정했는지
- 결과적으로 원래 크기로 복원된 이유
- 고정 조작부와의 겹침을 제대로 감지하는지
- 부모 요소의 높이 부족을 검사하는지
- 다른 문구 때문에 실패한 것을 등록된 문구의 실패로 판단했는지
- CSS 우선순위 또는 고정 line-height 문제인지

가능하다면 SDK 내부 상태를 읽기 전용으로 관찰하고, 불필요한 런타임 패치를 하지 마세요.

## 5. inspectLayout() 진단 정확도

현재 SDK의 `inspectLayout()`은 기본 글씨에서 실제 잘림이 없는데도 `text-clipped`를 반환한 사례가 있습니다.

다음 사항을 확인하세요.

- 실제 DOM에서 잘림이 있는지
- SDK가 어떤 기준으로 text-clipped를 판정하는지
- scrollHeight/clientHeight가 동일해도 경고가 나오는 이유
- 글씨 축소 실험 결과와 진단 결과가 일치하는지
- 실제 겹침이 있는데 진단이 놓치는 경우가 있는지
- 실제 문제가 없는데 진단이 경고하는 경우가 있는지

단순히 진단 결과가 정상이라고 표시된 것만으로 성공 처리하지 마세요.

## 6. 테스트 화면

다음 화면에서 검증합니다.

- 320×844
- 360×667
- 390×844
- 1080×1920

가장 중요한 것은 **360×667의 14px 및 16px 상태**입니다.

필요한 경우 v3 QR 하단 60·70·80% 모드도 비교하세요.

기존 SDK의 QR 도크 동기화 기능이나 화면 전환 기능은 변경하지 않습니다.

## 7. 범용 SDK 관점에서 판단

분석 결과를 다음 네 경우로 분류해 주세요.

**유형 A — 5~10% 축소로 실제 겹침이 완전히 해결되지만 SDK가 실패로 판정함**

→ 공통 SDK의 판정·보정 로직에 수정이 필요한 사례입니다.

**유형 B — 첫 번째 문구만 축소하면 해결되지 않지만, 두 문구가 함께 영향을 줌**

→ 보정 대상 및 부모 영역 측정 기준을 검토해야 합니다. 단, 개인정보 안내의 자동 축소는 허용하지 않습니다.

**유형 C — 글씨 크기를 10% 줄여도 실제 콘텐츠 높이가 충분히 줄어들지 않음**

→ 줄 높이, 부모 컨테이너, 고정 영역 등의 구조적 한계를 보고합니다.

**유형 D — QR 도크 또는 SDK 레이아웃 적용 과정에서 불필요한 공간이나 겹침이 발생함**

→ 공통 SDK 측의 도크 공간 계산 문제인지 확인합니다.

이 네 유형은 서로 중복될 수 있으므로 실제 결과를 기준으로 판단하세요.

## 8. 작업 범위 제한

이번 작업에서는 다음을 하지 않습니다.

- `src/styles.css` 영구 수정
- 호스트 레이아웃 변경
- 푸터 높이 변경
- SDK 소스 수정
- 새 SDK 버전 생성
- 개인정보 안내 영구 축소
- 큰 글씨 모드 해제
- 주요 버튼 글씨 축소
- 스마트 길잡이 수정
- AI 도입
- 자동 초기화 기능 추가
- 중앙 QR 서버·DB 변경
- Publish

진단용 스크립트가 필요하면 별도 테스트 파일로 만들되, 사용자 화면에 영향을 주지 않고 테스트 종료 후 스타일을 원래 상태로 돌리세요.
