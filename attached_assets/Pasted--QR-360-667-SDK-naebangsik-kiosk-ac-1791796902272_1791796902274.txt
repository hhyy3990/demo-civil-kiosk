# 내 방식 QR — 무인민원발급기 360×667 마지막 메뉴 아래 빈 공간 원인 진단

현재 무인민원발급기 프로젝트에는 공통 접근성 SDK `@naebangsik/kiosk-accessibility-sdk@0.5.5`가 정상적으로 설치되어 있습니다.

v0.5.5 적용 결과 다음 기능이 정상 동작함을 확인했습니다.

- 1440×900 상단 제목 잘림 해결
- 화면 전환 시 스크롤 초기화
- 최하단 스크롤 위치가 갑자기 되돌아가는 문제 해결
- QR v1/v2/v3 모의 프로필 적용
- 하단 60·70·80% 동작
- QR 도크·스마트 길잡이·스크롤 안내
- 주민등록등본 발급 전체 시뮬레이션

그러나 360×667 화면에서는 **증명서 목록을 끝까지 스크롤하면 마지막 메뉴가 화면 위로 지나가고 빈 공간이 남는 현상**이 확인됐습니다.

이번 작업의 목적은 이 현상의 원인을 정확히 판정하는 것입니다.

**이번에는 진단만 진행합니다. SDK, 앱 CSS, 업무 로직을 수정하지 마세요.**

## 1. 기존 문제 재현

브라우저 화면을 360×667로 설정합니다.

다음 세 가지 v3 모의 프로필을 각각 적용합니다.

- 큰 글씨·큰 버튼·고대비 + 하단 60%
- 큰 글씨·큰 버튼·고대비 + 하단 70%
- 큰 글씨·큰 버튼·고대비 + 하단 80%

첫 화면의 증명서 메뉴 18개를 대상으로 실제 스크롤을 수행합니다.

기존 측정 결과:

| 모드 | 마지막 메뉴가 보이는 위치 | 최대 scrollTop |
|---|---:|---:|
| 60% | 640 | 944 |
| 70% | 560 | 889 |
| 80% | 560 | 838 |

메뉴가 보이는 지점에서는 모두 클릭이 성공하지만, 끝까지 스크롤하면 메뉴가 화면 위쪽으로 지나갑니다.

위 값을 기준으로 동일한 현상이 재현되는지 확인합니다.

## 2. 실제 빈 공간을 만드는 요소 확인

`section#stage`의 내부 구조를 분석합니다.

다음 항목을 측정해 주세요.

- stage의 boundingClientRect
- scrollHeight
- clientHeight
- 최대 scrollTop
- 실제 마지막 메뉴의 위치와 크기
- 마지막 메뉴 다음에 존재하는 DOM 요소
- 마지막 메뉴 부모 요소의 boundingClientRect
- stage 하위 요소들의 실제 높이
- padding-top / padding-bottom
- margin-top / margin-bottom
- min-height / height / max-height
- flex-grow / flex-shrink / flex-basis
- justify-content / align-items
- grid 관련 정렬
- position / transform
- overflow-y

**마지막 메뉴 아래 빈 공간이 정확히 어떤 요소나 레이아웃 속성 때문에 만들어지는지 확인하는 것이 핵심입니다.**

DOM에 아무 요소가 없어도 min-height, flex 정렬, padding 등으로 공간이 생길 수 있으므로 실제 계산된 레이아웃을 조사해 주세요.

## 3. 콘텐츠 끝과 스크롤 끝 비교

다음 좌표를 실제로 계산해 주세요.

A. 마지막 증명서 메뉴의 아래쪽 좌표

B. 메뉴 목록 컨테이너의 아래쪽 좌표

C. 실제 콘텐츠 컨테이너의 아래쪽 좌표

D. stage의 스크롤 가능한 콘텐츠 끝 좌표

E. stage의 표시 영역 아래쪽 좌표

F. 최대 스크롤에서 마지막 메뉴가 표시 영역 위로 지나간 거리

특히 다음 값을 계산합니다.

`마지막 메뉴 이후의 실제 스크롤 가능 공간`

마지막 메뉴 뒤에 다른 필수 콘텐츠가 없다면, 왜 그 공간이 필요한지도 확인해 주세요.

단순히 빈 공간이 있다는 사실만 보고하지 말고 그 공간을 만들어내는 요소 또는 CSS 계산을 특정해 주세요.

## 4. SDK 적용 전후 비교

같은 호스트 화면을 다음 상태로 비교합니다.

1. QR 미적용 기본 모드
2. v3 viewportMode null
3. 하단 60%
4. 하단 70%
5. 하단 80%

가능하면 SDK의 정상 공개 API를 이용해 viewportMode를 비활성화하거나 전환합니다.

SDK 코드를 수정하거나 강제로 스타일을 제거하지 마세요.

각 상태에서 다음을 비교합니다.

- stage 높이
- 실제 콘텐츠 높이
- 최소 높이
- 스크롤 가능 거리
- 마지막 메뉴 뒤 여백
- 세로 정렬 방식
- 스크롤 소유자

이를 통해 **SDK 적용 전부터 존재하던 여백인지, 하단 viewport 적용 시 새로 생기는 여백인지**를 구분합니다.

## 5. 원인 분류

다음 세 가지로 구분합니다.

### A. 호스트 레이아웃 문제

무인민원발급기의 기존 CSS에서 불필요하게 큰 최소 높이, 여백, flex/grid 정렬 등이 마지막 메뉴 아래 공간을 만드는 경우입니다.

이때는 문제를 유발한 정확한 CSS 선언과 DOM 구조를 보고해 주세요.

다른 키오스크에서도 사용할 수 있는 일반적인 레이아웃 원칙을 제안하되 이번에는 수정하지 않습니다.

### B. 공통 SDK 문제

SDK의 하단 viewport 처리 또는 안전 중앙 정렬 보정 때문에 불필요한 공간이 발생하는 경우입니다.

이때는 어떤 SDK 처리 이후 여백이 증가하는지 근거를 제시해 주세요.

SDK 수정은 데모커피의 공통 SDK 프로젝트에서 진행할 예정이므로 이번 프로젝트에서는 수정하지 않습니다.

### C. SDK와 호스트의 상호작용 문제

호스트의 min-height·중앙 정렬 등은 기존에 존재했지만, SDK가 화면 높이를 제한할 때 빈 공간이 지나치게 커지는 경우입니다.

이때는 호스트가 SDK의 레이아웃 계약을 지키지 않은 것인지, SDK가 일반적인 호스트 구조를 더 안전하게 지원해야 하는 것인지 구분해 주세요.

**단순히 무인민원발급기에서만 발생한다는 이유로 호스트 문제라고 단정하지 마세요.**

## 6. 최소 변경 가설 검증 — 실제 코드 수정 금지

원인 후보가 확인되면 브라우저 DevTools 또는 일회성 테스트 fixture에서만 개별 속성을 바꿔 결과를 비교할 수 있습니다.

예시:

- min-height 변경
- padding-bottom 제거
- flex-grow 조정
- 세로 정렬 변경
- 콘텐츠 컨테이너 높이 조정

단, 다음 조건을 지킵니다.

- 앱 실제 소스 파일 수정 금지
- SDK 소스 수정 금지
- node_modules 수정 금지
- 영구 CSS 패치 금지
- 한 번에 여러 CSS 속성을 변경하지 않기
- 각 실험 후 기존 상태 복원
- 마지막 메뉴뿐 아니라 첫 제목·QR 도크·하단 고정 버튼도 검사

일회성 실험으로 여백이 사라졌다면 변경한 속성, 전후 수치, 다른 화면에 미친 영향을 보고해 주세요.

**목적은 해결책을 임시로 적용하는 것이 아니라, 원인을 증명하는 것입니다.**

## 7. 스크롤 및 클릭 접근성 검증

다음 세 위치에서 검사합니다.

- 스크롤 최상단
- 마지막 메뉴 전체가 보이는 위치
- 스크롤 절대 최하단

측정 항목:

- 실제 scrollTop
- 마지막 메뉴 top/bottom
- hit-test 결과
- 클릭 성공 여부
- 화면에 표시된 빈 공간 크기
- 스크롤 위치 안정성

실제 휠 및 Chromium 터치 에뮬레이션을 사용합니다.

스크롤 마지막 위치에서 메뉴가 보이지 않더라도 위로 조금 이동하면 클릭할 수 있는지 구분해 보고합니다.

다만 이것을 문제 해결로 간주하지는 않습니다.

특히 360×667과 390×844 사이에서 어떤 CSS breakpoint 또는 높이 제한 차이가 있는지 확인해 주세요.

단순히 화면 크기가 달라서 그렇다고 설명하지 말고, 실제 적용되는 레이아웃 속성 차이를 제시해 주세요.

## 9. 수정 방향 제안

원인을 확정한 뒤 다음 중 하나를 추천해 주세요.

**방향 1 — 호스트 레이아웃 계약 수정**

호스트가 SDK에 제공하는 스크롤 컨테이너 또는 레이아웃 구조를 일반적인 방식으로 수정하는 것이 적절한 경우입니다.

필요한 최소 변경 위치와 예상 효과를 설명합니다.

**방향 2 — 공통 SDK 개선**

정상적인 호스트 구조에서도 동일한 현상이 발생할 수 있어 SDK가 범용적으로 처리해야 하는 경우입니다.

독립 fixture 재현 가능성과 공통 SDK 수정 방향을 설명합니다.

**방향 3 — 실제 필수 콘텐츠에 따른 정상 여백**

마지막 메뉴 뒤에 실제 필요한 안내나 고정 조작부 회피 영역이 있어 여백이 의도된 경우입니다.

이때는 여백이 필요한 이유와 크기가 적절한지 설명해 주세요.

정상 동작이라도 마지막 메뉴가 최하단에서 화면 밖으로 완전히 사라지는 것이 고령층 사용성에 적절한지는 별도로 평가해 주세요.
