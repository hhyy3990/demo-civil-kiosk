# 내 방식 QR — 무인민원발급기 하단 조작 모드 오류 원인 조사 및 재현

현재 무인민원발급기에는 `@naebangsik/kiosk-accessibility-sdk@0.4.0`이 설치돼 있으며, 방법 B 하단 조작 모드를 개발용 설정으로 시험하고 있습니다.

실제 사용자가 하단 조작 모드를 직접 사용한 결과, 브라우저 자동화 테스트에서는 발견하지 못했던 심각한 접근성 오류 세 가지가 확인됐습니다.

이번 작업에서는 무인민원발급기의 실제 DOM과 스크롤 구조를 계측해 **원인을 확인하고 공통 SDK에서 재현할 수 있는 자료를 만드는 것**이 목적입니다.

아직 공통 SDK를 수정하거나 호스트 전용 임시 CSS로 문제를 감추지 마세요.

## 1. 최우선: 숫자 키패드 하단 접근 불가

주민등록번호 입력 화면에서 숫자 키패드의 위쪽 1~6은 보이지만, 아래쪽 7·8·9·0은 하단 고정 조작부 뒤에 가려집니다.

문제는 사용자가 손가락으로 화면을 끝까지 밀어도 키패드 아래쪽이 나타나지 않는다는 점입니다.

다음을 측정해 주세요.

- 실제 스크롤 소유 요소
- `scrollTop`, `scrollHeight`, `clientHeight`
- 최대 스크롤 거리
- 키패드 전체 bounding rectangle
- 0~9 숫자 버튼 각각의 bounding rectangle
- 하단 고정 조작부의 bounding rectangle
- 화면을 끝까지 내렸을 때 각 버튼의 노출 면적
- `elementFromPoint()`를 통한 터치 가능 여부
- viewport mode 60%·70%·80%별 차이
- 큰 글씨·큰 버튼·고대비 적용 시 차이

특히 **스크롤 최하단에서 7·8·9·0을 실제로 볼 수 있는지, 실제 브라우저 포인터로 누를 수 있는지** 확인해 주세요.

단순히 버튼이 DOM에 존재하거나 자동 클릭 이벤트를 호출할 수 있다는 이유로 성공 처리하면 안 됩니다.

## 2. 키패드 문제 원인 분리

다음 가능성을 구분해 조사해 주세요.

A. SDK가 하단 고정 조작부 높이를 잘못 계산하는 경우

B. SDK의 viewport shell 또는 내부 스크롤 컨테이너가 콘텐츠 마지막 부분을 잘라내는 경우

C. 호스트의 고정 높이·overflow 설정으로 스크롤 가능한 거리가 부족한 경우

D. 하단 조작부가 콘텐츠 위에 겹치지만 필요한 scroll clearance가 없는 경우

E. SDK가 실제 스크롤 소유 요소를 잘못 판단하는 경우

F. 다른 설정의 글씨 확대·버튼 확대 때문에 스크롤 범위가 달라지는 경우

각 가설에 대해 실제 DOM 좌표와 스크롤 수치를 근거로 판단해 주세요.

현재 SDK에서 이미 제공하는 안전 여백 API와 어댑터 등록이 올바르게 사용되고 있는지도 확인해 주세요.

**호스트 어댑터 연결 누락이라면 정확히 어떤 영역 등록이 필요한지 보고하고, SDK 공통 계산 결함이라면 해당 함수와 재현 조건을 보고해 주세요.**

## 3. 스크롤 안내 표시 시점 오류

사용자가 확인한 실제 동작:

- 화면 맨 위: 아래에 더 많은 메뉴가 있지만 스크롤 안내가 표시되지 않음
- 약 2/3 정도 스크롤: 안내가 갑자기 나타남
- 스크롤 최하단: 안내가 사라짐

원하는 동작:

- 처음부터 아래에 더 볼 내용이 있으면 안내 표시
- 스크롤 도중에는 계속 표시
- 최하단에 도달하면 숨김
- 다시 위로 올리면 재표시

**일반적인 스크롤 메뉴 버튼과 안내 pill이 시각적으로 일부 겹치는 것은 허용합니다.**

일반 메뉴 버튼을 모두 안내 회피 영역으로 등록해 스크롤 안내를 숨기는 정책은 이번 요구사항과 맞지 않습니다.

반면 처음화면·전화면·확인 등 고정된 필수 조작부는 보호해야 합니다.

### 조사할 항목

- SDK가 안내를 표시하지 않는 정확한 이유
- 안전 영역 계산 결과
- 어댑터에 등록된 회피 요소 목록
- 스크롤 위치별 안내 표시 상태
- 스크롤 위치별 스크롤 가능 여부
- 스마트 길잡이 또는 모달에 의한 일시 숨김 여부
- 60%·70%·80%별 차이

원인이 호스트에서 일반 메뉴 버튼 전체를 회피 대상으로 등록했기 때문이라면 해당 등록을 제거했을 때 안내가 정상적으로 표시되는지 개발용 실험에서 확인해 주세요.

단, 기존 필수 버튼 보호 기능은 유지해야 합니다.

## 4. QR 모달 열림·닫힘 시 스크롤 점프

QR 설정 팝업이나 발급 불가 메뉴 안내 팝업을 열면 배경 화면의 스크롤 위치가 바뀌는 현상이 확인됐습니다.

기존 자동화에서는 안내 모달을 열 때 `scrollTop`이 546px에서 439px로 이동하는 사례가 있었습니다.

실제 QR 설정 팝업에서도 같은 종류의 현상이 발생하는지 별도로 검증해 주세요.

다음 항목을 계측합니다.

- 모달 열기 직전 스크롤 위치
- 열림 직후 위치
- 100ms·500ms·1초 뒤 위치
- 모달 닫기 직후 위치
- 닫은 뒤 1초 위치
- 포커스가 이동한 요소
- document.activeElement
- 모달 열림 시 body/root의 overflow 변화
- viewport 높이·scrollHeight 변화
- SDK overlay 등록과 배치 변경 시점

특히 다음 원인을 구분합니다.

- 모달로 포커스가 이동하면서 브라우저가 자동 스크롤
- 스크롤 잠금 과정에서 좌표가 변경
- SDK viewport 재측정
- 호스트 모달 컴포넌트의 자동 포커스
- 브라우저 scroll anchoring
- 기타 호스트 코드

모달을 닫은 뒤 사용자가 이전에 보던 위치로 돌아오는지 확인해 주세요.

## 5. 최소 수정 허용 범위

이번 단계의 주목적은 원인 조사이지만, 다음과 같은 **안전하고 명확한 호스트 어댑터 연결 오류**는 수정해도 됩니다.

- 일반 스크롤 메뉴 버튼을 필수 회피 영역에서 제외
- 실제 하단 고정 조작부를 SDK에 올바르게 등록
- SDK가 이미 지원하는 기존 API의 잘못된 연결 수정

단, 수정 전후 결과를 모두 측정해 주세요.

다음 작업은 하지 마세요.

- 키패드 버튼을 개별적으로 위치 이동
- 원인 확인 없이 padding-bottom이나 margin-bottom을 큰 값으로 추가
- 스크롤 위치를 반복적으로 강제 조정
- 공통 SDK 내부 소스 수정
- 하단 조작 모드를 호스트 전용 CSS로 새로 구현
- QR 스키마 또는 중앙 서버 변경
- 기존 발급 업무 로직 변경

SDK 공통 결함이라면 무리해서 해결하지 말고 원인과 재현 자료를 보고해 주세요.

## 6. 브라우저 재현 환경

다음 화면을 사용합니다.

- 320×844
- 390×844
- 1080×1920

각각 하단 조작 비율:

- 60%
- 70%
- 80%

접근성 조합:

- 기본 글씨
- 아주 큰 글씨
- 아주 큰 글씨 + 큰 버튼 + 고대비

특히 **390×844, 하단 70%, 아주 큰 글씨 + 큰 버튼 + 고대비**를 핵심 재현 조건으로 사용합니다.

사용자가 직접 손가락으로 스크롤했을 때와 가깝도록 실제 브라우저 터치·휠 입력을 사용하고, 스크롤 좌표를 강제로 설정하는 자동화와 구분해 주세요.

## 7. 전체 발급 흐름 영향 확인

- 주민등록표(등본) 선택
- 개인정보 보호 안내
- 숫자 키패드 입력
- 가상 지문 확인
- 신청 항목 설정
- 신청 내용 확인
- 가상 결제 및 발급 완료
- 처음화면 복귀와 세션 초기화

키패드 접근 불가로 절차가 중단된다면 성공으로 보고하지 마세요.

테스트에는 임의의 숫자만 사용하고 실제 개인정보는 사용하지 않습니다.

### 최종 목표

**무인민원발급기에서 발견된 세 가지 오류를 정확히 재현하고, 공통 SDK에서 고쳐야 할 문제와 호스트 어댑터에서 해결할 문제를 분리하는 것입니다.**

특히 7·8·9·0을 누를 수 없는 현상을 최우선으로 조사해 주세요.

단순히 테스트를 통과시키기 위한 임시 화면 수정은 하지 말고, 측정 결과와 재현 조건을 남겨 주세요.
